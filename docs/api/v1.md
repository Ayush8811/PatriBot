# PatriBot API v1 (contract)

This is the contract between the FastAPI backend (`api/`, Phase 2) and the Next.js web app (`web/`, Phase 3). Both
sides build against this document. Changes need updating here first. JSON field names are snake_case. Times are
ISO 8601 with offset (`+05:30`). Dates are `YYYY-MM-DD`. Base path: `/api/v1`.

Predicted times come from `meta.eta_model`. In Phases 2–4 that is `"baseline_hist"`: the scheduled time plus the
historical delay percentiles per train × station (falling back to coarser averages when a train has little history).
In Phase 5 it becomes the LightGBM quantile model. Clients must not assume which model is in use.

**General rules** (agreed with the web app; all backward compatible with the first version of this document):
- **CORS** allows `http://localhost:3000` and `http://localhost:3100` by default (env `PATRIBOT_CORS_ORIGINS`,
  comma-separated, replaces the list).
- **OpenAPI** is served at `/api/v1/openapi.json` (Swagger UI at `/api/v1/docs`).
- Responses may gain **new fields** at any time; clients ignore fields they do not know. Fields marked *addition*
  below are such extensions.
- **`503 {"detail": "data unavailable: ..."}`** from any data endpoint when the warehouse or serving database cannot be
  read (not built yet, locked, Postgres down).

## GET /health
`200 {"status": "ok", "data_as_of": "2026-10-05T06:15:00+05:30", "eta_model": "baseline_hist"}`
(`503 {"status": "unavailable", "detail": "...", "eta_model": "baseline_hist"}` when no data can be read.)
`data_as_of` is the newest collected run's fetch time; it can be `null` before the first collection.

## GET /places/search?q=kolk&limit=10
Resolves cities, clusters and stations (FR-2).
```json
{"results": [
  {"kind": "cluster", "id": "KOLKATA", "name": "Kolkata (all stations)", "stations": ["HWH","SDAH","KOAA","SRC","SHM"]},
  {"kind": "station", "id": "HWH", "name": "Howrah Jn", "cluster": "KOLKATA"}
]}
```
`limit` is 1–50 (default 10). Clusters come before stations. A station's `cluster` is `null` when it belongs to no city
cluster (e.g. `GAYA`, a split hub); the key is always present. Cluster results have `stations`, station results have
`cluster`, never both. Aliases resolve (`bombay` → `MUMBAI`, `calcutta` → `KOLKATA`).

## POST /plan
Request:
```json
{
  "origin": "KOLKATA",                 // cluster id or station code
  "destination": "DELHI",
  "date_from": "2026-11-20",           // departure-date window (inclusive)
  "date_to": "2026-11-30",
  "preferences": {
    "overnight": true,                 // soft preference unless "hard": ["overnight"]
    "depart_after": null,              // "HH:MM" local
    "depart_before": null,
    "arrive_by": null,                 // "HH:MM" local on the arrival day; judged on P90 when hard
    "classes": ["3A", "2A"],           // optional filter
    "objective": "fastest",            // "fastest" | "most_reliable" | "balanced"
    "allow_split": true,
    "hard": []                         // subset of ["overnight","arrive_by","depart_after","depart_before","classes"]
  },
  "max_results": 10
}
```
Response `200`:
```json
{
  "query": { "...": "the normalised request, origin/destination resolved to station lists" },
  "itineraries": [
    {
      "id": "d-12301-2026-11-21",
      "kind": "direct",                // "direct" | "split"
      "score": 0.82,                   // higher is better, 0..1
      "score_breakdown": {"journey_time": 0.9, "reliability": 0.8, "preference": 1.0, "transfer": 1.0},
      "why": ["Fastest predicted journey in the window", "Overnight: departs 16:50, arrives ~10:40"],
      "legs": [
        {
          "train_no": "12301", "train_name": "Howrah Rajdhani", "train_type": "Rajdhani",
          "run_date": "2026-11-21",    // departure date from the train's origin
          "from_code": "HWH", "from_name": "Howrah Jn", "to_code": "NDLS", "to_name": "New Delhi",
          "dep_sched": "2026-11-21T16:50:00+05:30",
          "arr_sched": "2026-11-22T10:05:00+05:30",
          "arr_pred_p50": "2026-11-22T10:38:00+05:30",
          "arr_pred_p90": "2026-11-22T11:20:00+05:30",
          "journey_min_sched": 1035, "journey_min_pred_p50": 1068,
          "reliability": 0.74,          // P(arrival delay <= 30 min), 0..1
          "history_runs": 41,           // runs behind the prediction (0 = fallback estimate)
          "overnight": true,
          "classes": ["1A","2A","3A"]
        }
      ],
      "layover_min_sched": null,       // split only: leg2.dep_sched - leg1.arr_sched
      "layover_min_p90": null,         // split only: leg2.dep_sched - leg1.arr_pred_p90 (can be negative = risky)
      "split_kind": null,              // split only: "split_itinerary" (separate tickets) | "break_journey"
      "warnings": [],                  // e.g. "Separate tickets: a missed connection is not refundable"
      "irctc_url": "https://www.irctc.co.in/nget/train-search"
    }
  ],
  "meta": {"eta_model": "baseline_hist", "data_as_of": "...", "dates_searched": 11, "candidates_considered": 143,
           "bookable_from": "2026-10-05", "bookable_to": "2026-12-03"}   // ARP window (60 days); dates beyond are plan-only
}
```
Errors: `422` invalid request (FastAPI validation shape). `404 {"detail": "unknown place: XYZ"}`.

Request rules:
- `origin` / `destination`: a cluster id, a station code, a city alias (`"Kolkata"`, `"Bombay"`) or an exact station
  name. Overlapping origin and destination (e.g. `KOLKATA` → `HWH`) is a `422`.
- **Date window:** `date_from` ≤ `date_to`, at most **31 days** inclusive (`2026-11-01` … `2026-12-01`); longer is a
  `422`. Dates are **departure dates from the boarding station**.
- **`max_results`:** default **10**, values above **20** are capped at 20 (the normalised `query.max_results` shows the
  value used); below 1 is a `422`.
- Preference defaults: `overnight` null (no preference), `objective` `"balanced"`, `allow_split` `false`, `hard` `[]`.
  `HH:MM` fields must match `00:00`–`23:59`. A hard constraint only applies when the matching preference is set.
- *Addition:* `preferences.arrive_by_date` (`YYYY-MM-DD`, optional): the day `arrive_by` refers to ("reach by 09:00 on
  Nov 25"). Without it, `arrive_by` applies to each itinerary's own scheduled arrival day. With it, itineraries that
  arrive more than 24 h before the deadline do not count as meeting it.

Response notes:
- Itineraries are **diversified**: the best-scoring date of each distinct train (or train pair) first, in score order,
  then further dates of the same trains in score order. So `score` is not monotonic across the whole list.
- **Plan only:** `meta.bookable_from` = today (IST) and `meta.bookable_to` = today + 60 days (the advance reservation
  period). A leg whose `run_date` is after `bookable_to` cannot be booked yet: the itinerary is still returned, with a
  warning naming the date booking opens. Compare each leg's `run_date` with that window; there is no separate flag.
- `history_runs` = 0 means the prediction is a fallback (corridor average or timetable only); `reliability` is then
  pulled toward 0.5. *Addition:* `legs[].eta_basis` names the level used: `train_station_month`, `train_station`,
  `train_station_shrunk`, `train_route_scaled`, `corridor_route_scaled` or `none` (docs/phase2/planner-api.md).
- `split_kind` is always `"split_itinerary"` for now (separate tickets); `"break_journey"` (one ticket) needs fare
  rules and comes later.
- *Addition:* `query` also has `origin_kind`, `destination_kind` (`cluster` | `station`), `origin_stations` and
  `destination_stations`.

## GET /trains/{train_no}
```json
{"train_no": "12301", "train_name": "...", "train_type": "...", "origin": "HWH", "destination": "NDLS",
 "running_days": ["MON","TUE","WED","THU","FRI","SAT"], "classes": ["1A","2A","3A"], "corridors": ["KOL-DEL"],
 "route": [{"seq": 1, "code": "HWH", "name": "Howrah Jn", "arr": null, "dep": "16:50", "day": 1, "distance_km": 0,
            "delay_p50_min": 0, "delay_p90_min": 5, "history_runs": 41}]}
```
`404 {"detail": "unknown train: 99999"}`. Per stop, `delay_p50_min` / `delay_p90_min` are the predicted arrival delay
for runs in the current month, and are **`null` when `history_runs` is 0** (no history of this train to show).
`running_days` is in MON..SUN order at the train's origin; `classes` is `[]` when unknown.

## GET /trains/{train_no}/performance?months=3
```json
{"train_no": "12301", "runs": 41, "on_time_pct": 61.0,
 "by_month": [{"month": "2026-10", "runs": 25, "final_delay_p50": 22, "final_delay_p90": 64, "pct_within_30min": 63.0}],
 "recent_runs": [{"run_date": "2026-10-03", "final_delay_min": 28, "run_state": "complete"}]}
```
`months` is 1–24 (default 3), counted back from the train's latest collected run. `runs`, `on_time_pct` and
`by_month` use complete, non-disrupted runs only (`on_time_pct` is `null` without any); `recent_runs` lists the 10
newest attempted runs of any `run_state`. `404` for an unknown train.

## POST /chat (Phase 4, stub until then)
Server-sent events. Request: `{"session_id": "...", "message": "overnight train Kolkata to Delhi Nov 20-30"}`.
Events: `event: token` (`{"text": "..."}`), `event: itineraries` (the same shape as `/plan` → `itineraries`),
`event: done` (`{"usage": {"queries_left_today": 2}}`), `event: error` (`{"code": "...", "detail": "..."}`). Until
Phase 4 the endpoint answers with a fixed message plus the itineraries from a `/plan` call parsed by simple rules.

- `error.code` is one of `"quota_exhausted"` (the user's AI-chat quota is used up, FR-23), `"spend_guard"` (the global
  LLM budget paused free AI chat for the day, FR-24) or `"server_error"`; `detail` is human-readable. An `error`
  event ends the stream (no `done` follows). The stub only emits `server_error`.
- A message that cannot be planned (no date, unknown place, window over 31 days) is answered with a clarifying
  question as `token` events followed by `done`, not with an `error`.
- The `itineraries` event's data is a JSON array (the `/plan` `itineraries` value); it is omitted when no plan ran.
